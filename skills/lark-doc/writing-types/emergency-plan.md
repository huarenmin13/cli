# 应急预案写作指南

## Overview

生成**边界清晰、指令明确、权责对等、资源闭环**的实战级应急预案。核心交付标准：真实政企防总指挥会直接拍板或照做的方案，而不是落灰的"安全合规手册"。

## 范文参考

参照模板的范例，城市排水防涝应急预案，请阅读示例：[emergency-plan.sample.城市排水防涝应急预案.md](./samples/emergency-plan.sample.城市排水防涝应急预案.md)。

生成预案前 **MUST** 先阅读范文，对齐章节结构和格式规范。

范文是一份完整的政企防汛预案，示范了以下要点：
- 10章国标框架的完整结构和标题编号方式
- 指挥体系的条文写法（逐岗列明职务+职责）
- 分级响应的量化触发条件+编号式响应行动
- 编号体例：一级（1）（2）（3）、二级1）2）3）、三级①②③
- 背景、原则、定义先用整段说明，再进入响应动作条文
- 附录表格（联络清单、物资清单）的列规范
- 结尾固定表述

**阅读方式**：不必全文逐字读入上下文。重点扫描目录结构（章节标题层级）、第2章指挥体系写法、第6章应急响应里“先总述后条文”的节奏，以及附录表格列定义即可。

## 工作流

`
危机分诊 → 红线校验 → 场景引擎 → 主体范式 → 时间轴+PlanB → RACI → 格式渲染 → 约束校验
`

### Step 1: 危机快速分诊

静默执行。从三个维度唯一判定：

| 维度 | 选项 |
|------|------|
| 生命周期 | 事前防范 / 事发响应 / 事中相持 / 事后恢复 |
| 核心诉求 | 生命保全 / 底线合规 / 资产保活 / 声誉修复 / 社会维稳 |
| 交付受众 | 决策层 / 执行层 / 监管层 / 公众媒体 / 个人家庭 |

### Step 2: 绝对红线（不可逾越）

- **生命与法律优先**：人员疏散与急救绝对排在业务/财产保全之前；法定直报事项强制作为首要节点
- **合规边界**：不虚构具体法规条款号，用"法定要求及监管规章"等稳妥表述
- **伦理底线**：严禁掩盖犯罪、销毁证据的策略；高危情境仅输出防控、逃生、报警指引

### Step 3: 风险场景引擎

| 引擎 | 危机类型 | 处置重点 |
|------|---------|---------|
| Engine_A | 实体空间与生命安全 | 物理隔离、人群疏散、专业救援联动 |
| Engine_B | 信息系统与数字安全 | 断网、日志保全、容灾切换 |
| Engine_C | 业务运营与供应链断裂 | 生命线业务识别、替代资源 |
| Engine_D | 商业声誉与公共关系 | 事实核验、定调、次生切断 |
| Engine_E | 公共治理与社会协同 | 属地联动、权威发布 |
| Engine_F | 个人与家庭绝境 | 极简自救、隐蔽求援 |
| Engine_G | 综合型突发事件 | 总则体系、分级响应、跨界协同 |

### Step 4: 主体范式

| 主体 | 重心 |
|------|------|
| G端 | 维稳、权威发布、分级指挥链、公信力 |
| B1 强监管(金融/医疗) | 合规直报、弱势群体安全、双回路、审计留痕 |
| B2 重资产/制造 | 停机停线、危险源隔离、现场警戒 |
| B3 轻资产/互联网/商圈 | 超大客流疏散、系统连续性、舆情阻断 |
| C端 个人/家庭 | 第一响应人、老幼病弱特殊路线、安全屋 |

### Step 5: 时间轴与 Plan B

| 阶段 | 时间窗口 | 核心动作 |
|------|---------|---------|
| 先控/逃生 | 0-20分钟 | 隔离危险源、启动疏散、首报 |
| 响应/求援 | 20分-2小时 | 指挥体系启动、资源调度 |
| 相持/排查 | 2-24小时 | 全面处置、次生防范 |
| 恢复 | 24小时后 | 业务恢复、善后复盘 |

按需预设现实卡点（夜间熟睡、断网断电、决策人失联），严禁"瞬间全部到位"。关键动作必须有 Plan B。

### Step 6: 权责矩阵 (RACI)

- B/G端：闭环至岗，严禁"相关部门"
- C端：闭环至具体人

### Step 7: 格式渲染

| 格式 | 适用场景 | 结构 |
|------|---------|------|
| 正式预案成文型 | 法定预案 | 10章国标框架（见约束HC-4） |
| 企业专项处置型 | 企业预案 | 同10章框架，内容可精简 |
| 危机公关定调 | 公关危机 | 内部定调+对外声明+分渠道口径+媒体QA |
| 个人自救清单 | 个人/家庭 | 步骤极简、附带物资表 |
| 管理汇报型 | 向上汇报 | 结论前置→判断→建议→资源→风险 |
| 现场岗位型 | 一线岗位 | 场景→步骤→禁止事项→解除条件 |
| 演练推演型 | 演练脚本 | 目标→情景→角色→时间脚本→注入点→评估表 |
| 专项治理型 | 长期治理 | 界定→路径→分阶段抓手→机制保障 |

选择"正式预案成文型"或"企业专项处置型"时 MUST 阅读示例：[emergency-plan.sample.城市排水防涝应急预案.md](./samples/emergency-plan.sample.城市排水防涝应急预案.md) 对齐。

## 约束

### 红线（Hard Constraints）

- **HC-1 零正确废话**：没有触发条件/具体抓手/验收标准的空话套话一律抹除。例：将"注意用火安全"替换为"立即关闭燃气总阀，拔掉所有大功率电器插头"
- **HC-2 正文禁止表格和高亮块**：正文用条文线性叙述。表格仅用于附录（联络清单/物资清单等）。禁止 callout/高亮块。真实预案是正式公文，不存在这些元素
- **HC-3 生命优先**：人身安全场景下，疏散与急救排序绝对优先于业务与财产
- **HC-4 10章国标框架**：正式预案和企业预案必须遵循以下章节结构，标题编号无空格：
  1.总则 → 2.指挥体系和职责 → 3.应急准备 → 4.风险识别管控 → 5.监测预报预警 → 6.应急响应 → 7.紧急避险 → 8.信息报送及发布 → 9.善后工作 → 10.预案管理
- **HC-5 标题层级规范**：一级 <h1> 写 1.总则，二级 <h2> 写 1.1指导思想，三级如 1.3.1 xxx 用正文段落 <p> 承载，不用 <h3>。编号用阿拉伯数字+圆点，无空格
- **HC-6 编号体例**：一级用（1）（2）（3），二级用1）2）3），三级用①②③。手动编号写入正文，不使用自动编号列表
- **HC-7 结尾固定表述**：本预案由[编制单位]负责解释。 本预案自印发之日起实施。
- **HC-8 法规不虚构**：不编造法规条款号，引用法律名称用书名号《》包裹，法律名称间不加逗号顿号，末尾用"等，制定本预案。"
- **HC-9 单章节格式统一**：同一章节内选择一种表达方式贯彻到底（全条文/全表格/全列表），禁止混用。格式切换只发生在章节边界
- **HC-10 条文不滥用**：编号只用于岗位职责、响应动作、检查事项和附录清单；背景、原则、定义、说明先用完整段落写清，禁止把每句话都拆成（1）（2）（3）

### 禁止使用的非规范表述

| 禁止 | 替换为 |
|------|-------|
| "相关部门" | 具体部门名称 |
| "尽快处理" | 明确时间节点 |
| "注意安全" | 具体动作 |
| "及时上报" | 明确时限 |
| "加强防范" | 具体措施 |
| "妥善处理" | 具体步骤和验收标准 |
| "高度重视" | 具体动作和衡量标准 |

### Quality Gate

| # | 检查项 | 通过标准 |
|---|--------|---------|
| Q1 | 场景匹配 | 风险引擎匹配正确？ |
| Q2 | 红线守住 | 生命/法律/伦理底线？ |
| Q3 | 框架合规 | 10章完整？与范文对齐？ |
| Q4 | 动作明确 | 每个动作有触发条件+内容+验收标准？ |
| Q5 | 权责闭环 | 闭环至岗/至人，无"相关部门"？ |
| Q6 | 时间轴+PlanB | 黄金节点+现实冗余？ |
| Q7 | 格式统一 | 正文无表格/高亮块？单章节不混用？ |
| Q8 | 编号规范 | 标题编号、编号体例正确？ |
| Q9 | 可直接使用 | 拿去能执行/演练/上报？ |
| Q10 | 条文克制 | 编号只服务动作/职责？背景与说明未被拆成流水账？ |

## 飞书文档输出约束（Lark Doc 版 · 强约束）

当输出目标是飞书云文档（docx）时，本节为**最高优先级红线**。应急预案是法定/正式公文，飞书排版上的任何“好看”诉求都必须让位于公文规范。本节与本指南其它规则冲突时以本节为准；本节内部任一条被违反，视为**预案不合格，禁止交付**。

### 飞书格式绝对红线（Doc Hard Constraints，不可逾越）

- **DHC-1 强制 XML，禁止 Markdown 输出**：应急预案**必须**以 XML 格式喂给 `lark-cli docs +create/+update`，不接受 Markdown 输出。预案的指挥体系、分级响应、附录表格依赖 block 结构稳定，Markdown 会丢层级与样式信息。即便用户随口说“用 markdown”，也应优先按 XML 生成正式正文。
- **DHC-2 正文绝对禁止高亮块与表格**：延续 HC-2，飞书正文**禁止** `<callout>`、**禁止** `<grid>`/`<column>`、**禁止**正文 `<table>`。真实预案是公文，不存在这些元素。表格**仅允许出现在附录**（联络清单/物资清单等），且用标准 `<table><thead>...</thead><tbody>...</tbody></table>`。生命优先红线用正文第一段 `<p>` 表达，**不得**用 callout 强调。
- **DHC-3 10章框架映射到标题块**：HC-4 的 10 章必须逐章用 `<h1>` 承载，编号手写无空格：`<h1>1.总则</h1>`…`<h1>10.预案管理</h1>`。二级 `<h2>1.1指导思想</h2>`。
- **DHC-4 三级及以下用 `<p>` 不用标题块**：严格落实 HC-5——形如 `1.3.1` 的三级内容用正文段落 `<p>` 承载（编号写在段首文本里，如 `<p>1.3.1 监测责任分工……</p>`），**禁止**使用 `<h3>`/`<h4>`。飞书标题最多到 `<h2>`。
- **DHC-5 标题块不自动编号，全部手写**：飞书 `<h1>/<h2>` 不生成序号，章节号必须手写进标题文本，与 HC-4/HC-5 完全一致。
- **DHC-6 编号体例用手写文本，禁用自动列表**：落实 HC-6——一级（1）（2）（3）、二级1）2）3）、三级①②③，全部作为 `<p>` 正文文本手写。**禁止** `<ol seq="auto">`/`<ul>` 自动编号列表（自动列表会破坏公文编号体例）。
- **DHC-7 文档标题用 `<title>`**：预案名写入独立 `<title>`（如 `<title>XX市城市排水防涝应急预案</title>`），正文 `<h1>` 从 `1.总则` 开始，不重复预案名。
- **DHC-8 结尾固定表述照写**：正文末尾以 `<p>` 承载 HC-7 固定表述：`本预案由[编制单位]负责解释。` 与 `本预案自印发之日起实施。`，各占一段。
- **DHC-9 法规书名号原样保留**：HC-8 的《》书名号在 XML 文本中原样写出，不转义；仅 `<`/`>`/`&` 等结构字符按 DHC-10 转义。
- **DHC-10 XML 文本转义**：标签本身禁止转义；标签内文本遇 `<`→`&lt;`、`>`→`&gt;`、`&`→`&amp;`、换行→`<br/>`；属性值内 `"`→`&quot;`。
- **DHC-11 条文不滥用**：正文先写总述段；（1）1）①只用于职责、动作、清单，禁止把背景、原则、定义拆成流水账。
- **DHC-12 单章节格式统一落到 block**：延续 HC-9，同一章节正文全程 `<p>` 线性叙述，不在章节内插入附录表格；附录区与正文区严格分离。

### 飞书 CLI 生成提示

**前置**：首次先 `lark-cli auth login`；所有命令带 `--api-version v2`，默认 `--as user`。

**预案通常较长，必须“先建骨架，再逐章 `block_insert_after` 填充”**，禁止一次性把全文塞进 `--content`（会触发参数限制，且不利于逐章校验）：

```bash
# 1. 建骨架：title + 10 章 <h1> + 各章 <h2> + 简短占位
lark-cli docs +create --api-version v2 --content @skeleton.xml

# 2. 拿到 doc_id 与各章 heading 的 block_id 后，逐章填充正文（含手写编号条文）
lark-cli docs +update --api-version v2 --doc <doc_id> \
  --command block_insert_after --block-id <第1章_block_id> \
  --content @chapter_1.xml

# 3. 附录表格单独追加到末尾
lark-cli docs +update --api-version v2 --doc <doc_id> \
  --command block_insert_after --block-id <附录章_block_id> \
  --content @appendix.xml
```

`skeleton.xml` 形如：

```xml
<title>XX市城市排水防涝应急预案</title>
<h1>1.总则</h1>
<h2>1.1指导思想</h2>
<p>……</p>
<h1>2.指挥体系和职责</h1>
<h1>10.预案管理</h1>
```

**注意事项**：
- `--content @file` 仅接受 cwd 下相对路径，绝对路径报 `unsafe file path`。
- 逐章填充用 `block_insert_after --block-id <章节标题 block_id>`，不要用 `append`。
- 同一 block 只能 `block_replace` 一次；需再改请重新 `+fetch` 取新 block_id。
- `<title>` 会被自动提取为文档标题，骨架写了 `<title>` 就不要再用 `<h1>` 重复预案名。

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 正文用表格展示指挥体系 | 用条文逐岗列明职务+职责 |
| 用高亮块强调红线 | 用 <p> 正文第一段表达生命优先红线 |
| 用 <h3> 写1.3.1级别内容 | 用 <p> 承载，三级编号是正文不是标题 |
| 用自动编号列表 | 手动编号写入正文，保持公文格式 |
| 把背景、原则、定义全拆成（1）（2）（3） | 先用总述段写清，再把职责或动作单独编号 |
| 只讲原则不给动作 | 每条必须有触发条件+执行内容+验收标准 |
| 出现"相关部门""有关单位" | 必须闭环到具体部门名称或岗位职责 |
| 虚构法规条款号 | 用"依据《XX法》等法律法规"稳妥表述 |
| "瞬间全部到位"的伪流程 | 预设现实卡点+Plan B |
| 飞书文档里用 `<callout>` 强调红线 | 用正文第一段 `<p>` 表达生命优先 |
| 正文里塞 `<table>`/`<grid>` 排版 | 正文全 `<p>`，表格只进附录 |
| 用 `<h3>` 写 1.3.1 级内容 | 三级编号写进 `<p>` 段首文本 |
| 用 `<ol seq="auto">` 自动编号 | （1）1）①手写进 `<p>`，保公文体例 |
| 一次性把全文塞进 `--content` | 先建骨架，再 `block_insert_after` 逐章填充 |

## 飞书格式差量

- **附录的流程/职责/处置表格正当**：联络清单、物资清单、值班/处置分工等**附录表格**是本类型的正当富 block，全局克制红线不误伤它们；用标准 `<table><thead>…</thead><tbody>…</tbody></table>` 承载即可。
- **但正文以"标题+段落"为骨架，勿全表格化**：应急预案是正式公文，正文（指挥体系、分级响应、处置动作）必须以 `<h1>/<h2>` 标题 + `<p>` 段落/手写编号条文为骨架线性叙述，**表格只出现在附录**，不得为"看着清楚"把正文的指挥体系、职责、响应动作整段搬进表格（详见上文 DHC-2、HC-2）。正文区与附录区严格分离。
- **正当≠堆砌**：附录该用表格才用；无意义的 `<callout>` / `<grid>` 分栏 / 装饰性表格一律禁止，正文的生命优先红线用第一段 `<p>` 表达而非高亮块。
