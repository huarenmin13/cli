# 执行方案写作指南

## Overview

将模糊需求转化为**可执行、可推进、可检查、可交付**的高质量执行方案。核心交付标准：该场景里真正有经验的人会交付的方案，而不是"写得像 AI 很会规划"。

## 范文参考

参照模板的范例，企业项目上线执行方案，请阅读示例：[execution-plan.sample.企业项目上线执行方案.md](./samples/execution-plan.sample.企业项目上线执行方案.md)。

生成方案前 **MUST** 先阅读范文，对齐章节结构和格式规范。

范文示范了以下要点：
- Engine_B 企业项目推进型的7章节结构和标题编号方式
- 阶段拆解的条文写法（编号条文+每步含动作+标准）
- 关键动作章节的条文+子编号格式
- 责任分工、时间节奏、风险预案如何压缩成线性正文，而不是机械改成表格
- 单章节格式统一在飞书文档里的实际落地（正文短段优先，必要时再起条文）

**阅读方式**：重点扫描章节结构、第2章阶段拆解写法，以及第4-6章如何用短段和条文承载结构化信息，不必全文逐字读入。

## 工作流

`
场景识别 → 场景引擎匹配 → 双轴构建 → 约束校验
`

### Step 1: 场景识别 (Silent)

静默执行，绝不暴露推理过程。从四个维度唯一判定：

| 维度 | 选项 |
|------|------|
| 场景 | S1体制内 / S2项目推进 / S3管理汇报 / S4职场协同 / S5个人成长 / S6复杂攻坚 |
| 目的 | 向上汇报 / 向下布置 / 横向协调 / 内部执行 / 自我管理 / 争取支持 / 正式成文 |
| 受众 | 决策层 / 平级 / 下属 / 外部合作 / 自己 |
| 痛点 | 更易采纳 / 更易落地 / 避免假大空 / 兼顾专业与体验 / 复杂任务可推进 |

### Step 2: 匹配场景引擎

| 引擎 | 适用 | 结构 |
|------|------|------|
| Engine_A 体制内 | 公文/通知/专项行动/部署方案 | 1.背景依据 → 2.总体要求 → 3.重点任务 → 4.实施步骤 → 5.责任分工 → 6.保障机制 |
| Engine_B 项目推进 | 业务落地/产品上线/项目管理 | 1.项目目标 → 2.阶段拆解 → 3.关键动作 → 4.责任分工 → 5.时间节奏 → 6.风险预案 → 7.验收复盘 |
| Engine_C 管理汇报 | 向上汇报/请示/方案比选 | 1.当前问题 → 2.核心判断 → 3.建议路径 → 4.所需支持 → 5.预期收益 → 6.风险提示 |
| Engine_D 职场协同 | 团队协作/任务派发/责任分工 | 1.目标与范围 → 2.任务拆解 → 3.责任分工 → 4.时间节点 → 5.协同机制 → 6.风险提醒 → 7.验收标准 |
| Engine_E 个人成长 | 学习/习惯/求职/时间管理 | 1.目标澄清 → 2.阶段安排 → 3.行动清单 → 4.障碍预判 → 5.自反馈机制 → 6.复盘调整 |
| Engine_F 复杂攻坚 | 长期治理/专项整改 | 1.问题界定 → 2.总体目标 → 3.治理思路 → 4.分阶段任务 → 5.关键抓手 → 6.机制保障 → 7.风险应对 → 8.评估复盘 |

**风格要点**：
- Engine_A：正式、稳健、克制，公文气质，禁止过度共情
- Engine_B：强结果导向、动作导向、直接干练，禁止空泛战略
- Engine_C：结论前置、强判断、强提炼，禁止写成执行手册
- Engine_D：边界清晰、动作明确、责任到人，禁止模糊表达
- Engine_E：温暖坚定、小步推进，禁止官样文章/过度施压
- Engine_F：见全局+拆动作，禁止只讲愿景不拆抓手

### Step 3: 双轴构建

**A轴——专业度**：目标导向、可量化、任务拆解清晰、逻辑自洽、节点明确、责任清楚、资源闭环、风险预案、反馈验收

**B轴——真实性**：文体风格、结构顺序、语言正式度均服从场景引擎；信息密度关键前置；结构化信息优先写成短段或少量编号条文，表格只做例外不做默认

## 约束

### 红线（Hard Constraints）

- **HC-1 零正确废话**：没有动作的原则、没有判断的结构、无法执行的专业词汇 → 一律抹除
- **HC-2 先场景后语气**：不用统一腔调覆盖所有任务
- **HC-3 正文段落优先**：背景、判断、协同机制、风险说明先用短段写清，不把每句话都拆成分点
- **HC-4 列表只服务动作**：列表仅用于步骤、检查项、责任拆解、时间节点；单层建议 3-5 条，超过则拆小节或改回段落
- **HC-5 标题必须编号**：所有一级标题用 1.`2.`3. 编号，二级用 1.1`1.2，三级用 1.1.1。**禁止裸标题**（如"目标与范围"→必须写成1.目标与范围）。**禁止层级跳跃**
- **HC-6 单章节格式统一**：同一章节内选择一种表达方式贯彻到底（全条文/全列表/全短段），**禁止同一章节内混用**。格式切换只发生在章节边界
- **HC-7 表格降级使用**：执行方案默认不用表格。只有用户明确要求对照/台账/字段矩阵，且文字表达明显不清时，才允许使用小表；责任分工、时间节奏、风险预案优先改写为短段或条文
- **HC-8 禁止过度装饰**：不为了"好看"堆砌装饰性元素，每个视觉块必须有信息承载理由
- **HC-9 文字为主**：能用一段话说清的不用高亮块，能用一句话点明的不用分栏
- **HC-10 不机械套模板**：必要时重点展开，次要弱化
- **HC-11 允许人味**：可接住痛点，但禁止表演式煽情

### 视觉约束（按引擎分级）

| 引擎 | 高亮块 | 分栏 | 表格 | 总体原则 |
|------|--------|------|------|---------|
| Engine_A | 禁用 | 禁用 | 默认不用 | 克制、庄重、纯条文优先 |
| Engine_B | 禁用 | 禁用 | 默认不用，确需对照时最多1张小表 | 干练、线性推进 |
| Engine_C | 禁用 | 禁用 | 仅方案比选时最多1张小表 | 精炼、判断导向 |
| Engine_D | 禁用 | 禁用 | 默认不用 | 清晰、责任闭环 |
| Engine_E | 禁用 | 禁用 | 默认不用 | 温和、轻量 |
| Engine_F | 禁用 | 禁用 | 复杂矩阵时最多1张小表 | 体系化，但正文仍线性 |

## 飞书文档输出约束（Lark Doc 版 · 正文克制优先）

当输出目标是飞书云文档（docx）时，在以上规则之外**叠加**以下飞书专属约束。本节只在 `skills-doc` 副本中生效，用于约束通过 `lark-cli docs` 创建/更新的正式文档输出。飞书文档默认骨架是**标题 + 短段 + 少量必要条文**，不是把结构化信息一律翻成表格、分栏和高亮框。

### 飞书格式红线（Doc Hard Constraints）

- **DHC-1 默认 XML，不默认 Markdown**：除非用户明确要求 Markdown，统一以 XML 格式喂给 `lark-cli docs +create/+update`。XML 表达力强、block 稳定、可被 `block_insert_after` 精准编辑；Markdown 导入后更容易丢结构，且不利于后续局部修订。
- **DHC-2 禁高亮块（callout）**：执行方案是正式工作产出，**禁止**使用 `<callout>` 高亮框。需要强调的结论用 `<p><b>...</b></p>` 加粗段落或独立小节承载，不靠装饰块抢眼。
- **DHC-3 禁分栏装饰**：禁止用 `<grid>`+`<column>` 做版面分栏装饰。并列两段叙事拆成两段 `<p>` 即可。
- **DHC-4 正文默认禁表格**：执行方案正文默认不用 `<table>`。只有用户明确要求矩阵/台账/字段对照，且文字表达明显变差时，才允许使用**1 张小表**；责任分工、时间节奏、风险预案优先改写为短段或条文。若例外使用表格，必须满足 `<table><thead>...</thead><tbody>...</tbody></table>` 三层结构，表头 `<th>` 统一 `background-color="light-gray"`。
- **DHC-5 标题手动编号**：飞书 `<h1>~<h9>` 不会自动生成序号。所有一级/二级/三级编号必须手写进标题文本，例：`<h1>1.项目目标</h1>`、`<h2>1.1总体目标</h2>`、`<h3>1.1.1关键结果</h3>`。编号与文字之间无空格，与 HC-5 一致。
- **DHC-6 标题层级 ≤ 4 级**：飞书语法上限 `<h9>`，但写作层级**最多到 `<h4>`**。继续细分用编号列表或编号段落承载，不再开新标题级别。
- **DHC-7 文档标题用 `<title>`**：文档标题写在独立 `<title>` 标签里且全文唯一，正文 `<h1>` **不要重复**输出文档标题。例：`<title>云盾产品上线执行方案</title>` 之后正文从 `<h1>1.项目目标</h1>` 开始。
- **DHC-8 段落优先**：每个 `<h1>/<h2>` 后先有 1 段总述 `<p>`；背景、判断、协同机制、风险说明用 `<p>` 承载，不要起列表。
- **DHC-9 列表必须节制**：`<ol><li seq="auto">...</li></ol>` 或 `<ul><li>...</li></ul>` 只用于步骤、检查项、并列动作。单层建议 3-5 项，单个 `<h2>` 下原则上不超过 1 组列表；列表项必须写完整句，不写残缺短语。
- **DHC-10 禁机械分点**：如果内容只是解释、判断、说明，不要拆成“一句一条”；优先合并回 1-2 段正文。
- **DHC-11 XML 文本转义**：标签本身禁止转义；标签内**文本**遇到 `<`→`&lt;`、`>`→`&gt;`、`&`→`&amp;`、换行→`<br/>`。`"` 在属性值内用 `&quot;`。
- **DHC-12 单章节格式统一在 Doc 层面落地**：同一 `<h2>` 下默认是“总述段 + 一组必要列表”或“连续短段”，不要 `<p>` 与 `<ol>` 与 `<table>` 来回切换；格式切换尽量发生在下一个 `<h2>` 之后。

| 引擎 | callout | grid 分栏 | table | 备注 |
|------|---------|-----------|-------|------|

### 飞书 CLI 生成提示

**前置**：首次使用先 `lark-cli auth login`；所有命令默认 `--as user`、`--api-version v2`。

**短方案（≤ 一屏）一次性创建**：

```bash
lark-cli docs +create --api-version v2 \
  --content @plan.xml
```

`plan.xml` 内容形如：

```xml
<title>云盾产品上线执行方案</title>
<h1>1.项目目标</h1>
<p>本方案围绕功能冻结、公测发布和正式上线三段推进，先收口范围，再压实责任，最后完成灰度与全量发布。</p>
<h2>1.1总体目标</h2>
<p>...</p>
```

**长方案：先建骨架，再分章 `block_insert_after` 填充**（避免一次性 `--content` 触发参数限制）：

```bash
# 1. 建骨架：title + 各级 heading + 简短占位
lark-cli docs +create --api-version v2 --content @skeleton.xml
# 2. 拿到 doc_id 与各 heading block_id 后，逐章追加正文
lark-cli docs +update --api-version v2 --doc <doc_id> \
  --command block_insert_after --block-id <h1_block_id> \
  --content @section_1.xml
```

**注意事项**：
- `--content @file` 只接受 cwd 下的**相对路径**，绝对路径会报 `unsafe file path`。
- 逐章填充用 `block_insert_after --block-id <章节标题 block_id>`，不要用 `append`（append 等价于追加到文档末尾）。
- 每章先插入总述 `<p>`，再补必要条文；不要一上来贴整块列表或表格。
- 同一 block 只能 `block_replace` 一次，多次替换需重新 `+fetch` 拿新 block_id。
- `<title>` 与 Markdown `#` 会被自动提取为文档标题，骨架里写了 `<title>` 就不要再写 `<h1>` 同名标题。

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 裸标题"任务拆解""责任分工" | 编号：2.任务拆解 3.责任分工 |
| 同一章节内短段→列表→表格来回切 | 选一种格式贯彻全章节，切换在章节边界 |
| 把责任分工/时间节奏/风险预案一股脑做成表格 | 优先改写成短段或编号条文，表格只作极少数例外 |
| 统一腔调覆盖所有场景 | 先识别场景，再匹配引擎风格 |
| 堆砌高亮块/分栏/装饰 | 能用文字说清的不用视觉块 |
| 有1.1没有1.2，层级跳跃 | 编号连续完整 |
| 一个小节下连着两三组列表 | 先写总述段，只保留一组必要列表 |
| 每句话都拆成 bullet | 合并回 1-2 段完整正文，再把动作部分单独起条文 |
| 飞书文档里用 `<callout>` 强调结论 | 用 `<p><b>...</b></p>` 加粗段落 |
| 用 `<grid>` 做版面分栏 | 并列叙事拆两段 `<p>`，不要做人为版式花样 |
| 标题里不写编号靠飞书自动生成 | 编号手写进 `<h1>~<h4>` 文本 |
| `<li>` 文本里手写“1. 2. 3.” | 用 `<ol><li seq="auto">` 自动编号 |
| 一次性把长方案塞进 `--content` | 先建骨架，再 `block_insert_after` 逐章填充 |

## 飞书格式差量

执行方案的飞书载体适配已在上文「飞书文档输出约束（Lark Doc 版）」完整写明，此处只做索引与差量归纳，通用克制红线仍守 lark-doc-style.md：

- 正当用法：默认以 XML 喂 `lark-cli docs +create/+update`（DHC-1）；表格默认禁用（DHC-4），只有用户明确要求矩阵/台账/字段对照且文字表达明显变差时，才按引擎分级允许**至多 1 张小表**（Engine_B 台账、Engine_C 方案比选、Engine_F 复杂矩阵），且须满足 `<thead>/<tbody>` 三层结构、表头 `background-color="light-gray"`。责任分工、时间节奏、风险预案优先改写为短段或条文。
- 非滥用：禁 `<callout>` 高亮块、禁 `<grid>` 分栏装饰、禁把结构化信息一律翻成表格；能用一段话说清的不用高亮块、能用一句话点明的不用分栏。旧范文里的表格只用于说明字段，不代表正文应继续表格化。
