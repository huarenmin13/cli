# 项目计划设计

使用本 skill 时,目标不是"列一个看起来完整的计划",而是产出能被真实项目负责人拿去推进、分工、协同、汇报或追踪的项目计划内容。

## 适用于什么

用户需要以下任一内容时,使用本 skill:

- 项目计划书、项目推进方案、实施计划、行动计划。
- 专项工作方案、治理方案、落地方案、上线计划。
- 项目阶段拆解、WBS、任务清单、里程碑、排期。
- 责任分工、协同机制、资源需求、风险预案、验收标准。
- 面向领导的项目汇报、请示方案、资源申请材料。
- 对已有项目计划进行补全、优化、改写或压缩。

## 不适用于什么

以下任务不应调用本 skill:

- 单纯个人待办清单或日程安排。
- 学习计划、旅行计划、健身计划等非项目推进类计划。
- 战略规划、年度规划、业务发展规划、转型规划等以方向判断、战略取舍、长期路径为核心的内容。
- 营销策划、品牌认知、产品上市、内容种草、活动战役、增长转化、客户经营、渠道动销、整合营销等以人群、卖点、传播、渠道和转化为核心的内容。
- 纯创意 brainstorm,不涉及落地推进。
- 只要一句简短建议或口号式方案。
- 不需要目标、任务、责任、资源、风险、验收等项目要素的轻量问题。

## 核心原则

- 计划必须围绕"如何推进项目"展开,写清为什么做、做什么、怎么做、谁来做、何时完成、如何验收。
- 不把结构完整误当成计划完整;缺少责任、资源、风险、验收的计划不能算可落地。
- 不机械生成大而全方案。用户只要局部模块时,只输出对应部分。
- 不重复堆同一类信息。目标、任务、风险、验收各写各的,不在多个章节反复说同一件事。
- 不写空泛套话、培训稿腔、AI 腔或无法执行的原则表述;参考文末「避免以下空表达」。
- 信息不足时可基于常识补合理假设;关键缺口会影响计划真实性时,按「必须追问的信号」处理。

## 信息识别

写计划前,内部识别以下信息:

- 项目类型:产品上线、活动执行、运营推进、系统建设、专项治理、跨部门协同、内部管理或其他。
- 项目阶段:立项筹备、启动、执行、中期纠偏、冲刺、复盘。
- 使用场景:内部执行、向上汇报、跨部门协同、资源申请、节点推进、正式成文、对外呈现。
- 面向对象/汇报层级:执行同事 / 项目负责人 / 部门负责人 / 总监及以上(措辞深度和篇幅随之调整)。
- 核心诉求:用户更需要完整方案、推进抓手、责任落实、时间排布、风险可控、资源申请,还是汇报表达。
- 现实约束:时间紧、资源少、协同复杂、目标高、依赖多、风险大、信息不充分等。
- 预算/规模量级(粗略即可):小型活动(<10 万)、中型项目(10-100 万)、大型专项(>100 万)或系统级建设。影响风险、资源、合规模块的展开深度。
- 输出范围:完整计划、局部计划、单个模块、简版摘要、正式文本、执行表格或汇报稿。

## 完整计划与局部计划判断

### 生成完整计划

当用户表达以下需求时,输出完整项目计划:

- "写一份项目计划书"
- "出一个完整推进方案"
- "给我一个实施计划"
- "做一个从启动到落地的计划"
- "用于汇报/立项/正式成文的项目方案"

完整计划通常应覆盖:背景或问题、目标、阶段安排、关键任务、时间节点、责任分工、资源需求、风险预案、协同机制、验收与复盘。

### 只生成局部计划

当用户只要求以下内容时,不要扩写成完整计划:

- 只要时间排期:输出阶段节点、里程碑和交付物。
- 只要任务拆解:输出 WBS、任务颗粒度、动作和产出。
- 只要责任分工:输出主责方、协同方、支持方、接口和交付边界。
- 只要风险预案:输出风险项、影响、预警信号、应对措施和责任人。
- 只要汇报版:输出结论前置的汇报材料,不展开成过细执行稿。
- 只要正式通知或成文文本:输出规范正文,不强行表格化。

### 信息不足时的处理

**必须追问的信号**(任意 1 条即追问,最多 3 个问题,按优先级排序):

- 没有项目目标,或目标纯口号(如"加强数字化建设")。
- 没有任何时间约束,连"近期""本月""Q3"这类相对时间都没有。
- 关键责任主体不明且项目涉及跨部门。
- 用户明确提到"高风险""大投入""涉及合规/财务/法务"却无任何约束信息。

**不应追问,直接给可改版本**:

- 用户明确说"先给一版""先出个框架""后续再调"。
- 只是缺项目名称、具体人名这种可留占位符的信息。
- 缺少时间但可用相对时间("T+3""第 1 周""第 2 周")推进。

处理策略:

- 缺少项目名称、时间、人员等信息,但仍可合理补齐时,直接用通用占位(如 `[项目名称]` `[负责人]` `[第 1 周]`)或合理假设生成。
- 用户要求"先给一版"时,不追问,直接生成可修改版本,并在开头一句话说明关键假设。

## 输出模式

根据项目语境选择最合适的模式,不要在最终答案中说明内部模式判断。

当用户要求"给模板""套一个结构""按不同场景推荐计划框架",或当前计划场景复杂、需要选择合适结构时,读取示例：[project-plan.sample.项目计划模板.md](./samples/project-plan.sample.项目计划模板.md)，选择最匹配的模板并按用户信息裁剪。

### 执行推进型

适用于业务落地、项目启动、专项执行、内部推进。

表达风格:直接、务实、动作导向。

常用结构:

- 项目目标
- 阶段划分
- 关键任务
- 时间节点
- 责任分工
- 风险预案
- 验收复盘

**排期与里程碑表**(至少选一张):

| 阶段 | 关键任务 | 产出物 | 责任人 | 时间节点 | 依赖 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 启动 | 明确目标与范围 | 项目章程 / 范围文档 | [项目经理] | 第 1 周 | - |
| 筹备 | 资源与方案对齐 | 方案稿 / 预算表 | [主责部门] | 第 2 周 | 启动完成 |
| 执行 | 关键动作推进 | 阶段性产出 | [执行组] | 第 3-6 周 | 筹备完成 |
| 验收 | 结果检查与复盘 | 验收报告 / 复盘纪要 | [验收方] | 第 7 周 | 执行完成 |

**责任分工表**:

| 事项 | 主责方 | 协同方 | 支持方 | 交付物 | 节点 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 目标对齐 | [产品/项目组] | [业务方] | [管理层] | 目标确认稿 | T+3 |
| 方案执行 | [执行组] | [支持组] | [IT/财务/法务] | 阶段性产出 | 按阶段 |
| 风险跟进 | [主责方] | [协同方] | [支持方] | 风险更新记录 | 每周 |

### 汇报请示型

适用于向上汇报、申请资源、争取支持、方案汇报。

表达风格:结论前置、重点明确、判断清晰。

常用结构:

- 项目背景
- 当前问题
- 核心目标
- 推进思路
- 关键举措
- 所需支持
- 风险提示
- 预期结果

**汇报语气约束**:
- 不替用户做出承诺或代表领导/某部门表态。
- 不出现未经用户确认的具体金额、ROI 或承诺性数据。
- "所需支持"写清楚:需要谁 / 做什么决策 / 在什么时间前,不写"请领导多多支持"。

**汇报摘要表**(可选放开头):

| 要点 | 结论 | 需要的支持 |
| :--- | :--- | :--- |
| 要做什么 | [一句话目标] | [需要谁 + 什么决策 + 时间] |
| 关键路径 | [3 个关键阶段] | [需要资源/人力/预算] |
| 风险与建议 | [1-3 个高风险 + 应对] | [需要拍板的事项] |

### 协同拉通型

适用于跨部门协作、多人协同、任务拉通。

表达风格:边界清晰、接口明确、责任清楚。

常用结构:

- 项目范围
- 工作分层
- 分工机制
- 时间节奏
- 协同机制
- 问题升级路径
- 验收标准

**协同与接口表**:

| 模块 | 主责方 | 协同方 | 接口人 | 交付物 | 节点 | 升级路径 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 模块 A | [部门 1] | [部门 2 / 部门 3] | [姓名/岗位] | [文档/数据/系统权限] | [时间] | [问题→负责人→升级至管理层] |

### 正式成文型

适用于制度化文本、正式材料、通知附件、成文计划。

表达风格:规范、稳健、正式。以条文化正文为主,谨慎使用表格。

常用结构:

- 项目背景
- 总体目标
- 重点任务
- 实施步骤
- 保障措施
- 责任分工
- 工作要求

成文格式建议:
- 标题层级统一使用 H1(项目名)、H2(一级章节)、H3(小节)。
- 条文化采用"一、二、三…… / (一)(二)(三)…… / 1. 2. 3.……"的层级结构,避免多级嵌套过深。
- 关键约束用加粗或引用块强调,但整体保持公文风格。

### 系统攻坚型

适用于复杂专项、长期治理、重点难题推进。

表达风格:兼顾全局判断与落地抓手。

常用结构:

- 问题界定
- 总体目标
- 治理思路
- 分阶段任务
- 关键抓手
- 保障机制
- 风险应对
- 评估复盘

**风险与应对表**(系统攻坚型必含):

| 风险 | 影响 | 预警信号 | 应对动作 | 责任人 |
| :--- | :--- | :--- | :--- | :--- |
| [举例:核心成员变动] | [延期 / 目标不可达] | [关键岗位请假、招聘进度 >4 周] | [备岗方案 / 招聘加速 / 任务临时转交] | [部门负责人] |
| [举例:依赖方不可控] | [关键路径阻塞] | [依赖方交付超 T+5] | [提前对齐 / 设定替代方案 / 升级至更高层级] | [项目负责人] |

## 内容要求(每个小节各附"避免写法 / 推荐写法"对照)

### 目标

- 写清项目总目标、阶段目标和关键结果。
- 区分核心目标与配套目标。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "提升效率、加强协同、保障落地" | "本季度把 XX 流程平均处理时长从 48h 压缩到 24h;上线 XX 系统 1.0,覆盖 3 个核心部门" |

### 任务

- 将项目拆到可执行动作,而不是停留在方向。
- 每项任务尽量包含动作、产出物、责任方和完成节点。
- 不把所有任务写成同等优先级,要识别关键路径和重点抓手。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "加强系统建设、推进上线工作" | "完成 XX 系统需求评审 → 开发 → 测试 → 灰度 → 正式上线;每一阶段有产出物与责任人(详见任务表)" |

### 路径

- 体现推进顺序、前后依赖和可并行事项。
- 对复杂项目写出阶段逻辑,不把任务简单堆成清单。
- 对紧急项目优先写关键路径和最小可落地版本。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "分阶段推进、齐头并进" | "阶段 1:目标对齐(1 周);阶段 2:方案与资源(2 周);阶段 3:执行与检查(4 周);阶段 4:验收与复盘(1 周);阶段 2 与 3 间存在方案→执行的前置依赖" |

### 时间

- 设置阶段节奏、关键里程碑和检查节点。
- 时间未知时,用"第 1 周 / 第 2 周""T+3 / T+7"等相对时间表达。
- 避免安排失真,不在过短周期内塞入明显无法完成的任务。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "尽快完成、近期上线" | "第 1 周:项目启动;T+3:目标确认;第 2 周:方案稿;第 3-5 周:执行;第 6 周:验收" |

### 责任

- 写清主责方、协同方和支持方。
- 明确谁牵头、谁配合、谁交付、谁验收。
- 多部门项目要写清接口关系和问题升级路径。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "各部门协同推进" | "产品部牵头主责;技术部、运营部协同;财务部、法务部支持;接口人为 XXX;问题先报接口人,48h 未解决升级至部门负责人" |

### 资源

- 识别人力、预算、物料、系统、数据、权限、供应商、外部支持等关键条件。
- 不只写动作,也要写完成动作所需支撑。
- 资源缺口要转成需要决策或协调的问题。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "需要一定资源保障" | "预计需:2 名产品 / 4 名研发 / 预算 20 万(含采购 XX);当前缺口:1 名研发、10 万预算 → 需在 T+7 前完成人力与预算决策" |

### 风险

- 前置识别关键卡点、依赖项、推进阻力和失控风险。
- 风险预案要具体到预警信号、应对动作和责任方。
- 不写"加强沟通""提前准备"这类没有动作的空预案。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "风险可控、加强预案" | "风险:核心成员变动;影响:关键路径延期 2 周;预警信号:关键岗位请假 / 招聘超 4 周;应对:备岗方案 / 任务临时转交;责任人:部门负责人" |

### 验收

- 写清阶段检查方式、最终验收标准、偏差纠正方式和复盘机制。
- 验收标准要能检查,尽量包含交付物、指标、结果状态或确认人。
- 不把"完成项目"当作验收标准。

| 避免写法 | 推荐写法 |
| :--- | :--- |
| "按计划完成、做好总结" | "阶段验收:每周产出与进度对照;最终验收:XX 系统上线 + 核心流程跑通 + 关键指标达标(处理时长 ≤24h);验收人为产品负责人 + 业务负责人签字;偏差 >20% 时启动纠偏会" |

## 避免以下空表达

以下写法"看起来完整"但不可执行,应替换成有动作、有责任、有节点的表达:

- "加强沟通、定期推进、提高效率、确保质量、强化执行、保障落地"。
- "成立专项小组、制定详细方案、加强督导、稳步推进、压实责任"。
- "风险可控、加强预案、提高认识、统一思想、加强领导"。
- "请领导多多支持、望各部门积极配合、相关同事共同努力"。
- 没有数字、没有责任人、没有时间、没有产出的任何段落。

## 文档版排版约束

将战略写入、改写或整理到飞书文档/Lark Doc 时,默认以「纯文字公文式排版」为主,避免为了"美化""结构化"而大量使用装饰性块级组件。

### 排版设计

- 标题层级统一使用 H1(文档/计划总名)、H2(一级章节)、H3(小节),不做更深层级标题嵌套。
- 正文使用普通 Markdown 段落表达,以文字陈述为主,结构通过标题与自然段落体现。
- 党政机关、事业单位、企业等创作场景的战略规划文本,优先采用纯文字公文式排版。

### 排版约束

- 除非用户明确要求,严禁大篇幅使用表格、高亮块、引用块、信息提示块、Callout、代码块、分栏、卡片、颜色底纹或任何装饰性块级组件。
- 数据、模型图示、排期对照、责任对照等少数场景,允许适量使用表格与图表;但必须对文字内容形成增益,起到锦上添花、画龙点睛的作用。
- 表格、图表、高亮块不得占据文字的主导地位,若仅为"让结构看起来完整"而使用,应视为冗余并删除。
- 逻辑分析、问题说明、风险论证、正式成文内容,一律优先使用正文段落表达。

## 表达与格式

- 用户指定结构、篇幅或文体时,优先遵循用户要求。
- 执行推进类可使用阶段结构、条目清单、WBS 或责任分工表。
- 汇报请示类应结论前置,突出判断和需要支持的事项。
- 正式成文类以规范正文和条文化表达为主,谨慎使用表格,详见「文档版排版约束」。
- 协同拉通类突出接口、边界、责任和机制,必要时使用对照表。
- 表格只用于并列信息、责任对照、时间节点、里程碑、风险清单等场景。
- 逻辑分析、问题说明、风险论证、正式成文内容优先使用正文。

## 篇幅控制

- 完整计划默认输出 1500-2500 字(约 1-2 页可读长度),超过时主动拆主次,保留核心路径,把细节挪入附录或后续可展开项。
- 用户要求"简版""一页纸""摘要"时,必须 ≤800 字,采用「结论 - 关键任务(3-5 条) - 需要支持」三段压缩结构。
- 大型项目(>100 万、>3 个月)可超出默认上限,但需先给出总览摘要,再进入详细章节。

## 输出前自检

最终输出前确认:

- 输出范围与用户需求一致,没有把局部需求扩写成完整计划。
- 目标清晰,能看出项目为什么做、做到什么程度。
- 任务拆到可执行层,关键动作、节点和产出明确。
- 推进路径合理,体现阶段、依赖和优先级。
- 责任清楚,主责、协同、支持和验收边界明确。
- 资源条件闭环,关键支撑和资源缺口有交代。
- 风险前置,预警和应对措施具体到责任人与动作。
- 验收可检查,有阶段检查、最终标准或复盘安排。
- 文风符合场景,能直接用于推进、沟通、汇报或成文。
- 篇幅与用户要求(完整 / 简版 / 一页纸)匹配。
- 没有出现未用户确认的具体金额、ROI 或承诺性数据;没有替用户代表领导或部门表态。

## 飞书格式差量

项目计划落到飞书在线文档时，通用克制红线守 lark-doc-style.md（禁 callout/高亮块与分栏装饰、标题手动编号），本类型只补以下差量：

- 正当用法：项目计划是本文档体系里少数**默认允许成套表格**的类型——排期与里程碑表、责任分工表、协同与接口表、风险与应对表在执行推进/协同拉通/系统攻坚场景下是核心承载物，可按上文对应模板正常使用。这类"并列信息、责任对照、时间节点、里程碑、风险清单"正是表格的正当场景。
- 非滥用：表格只用于上述结构化并列信息；逻辑分析、问题说明、风险论证、正式成文内容一律优先用正文段落。正式成文型（Engine 正式成文）仍以条文化正文为主、谨慎用表格，不为"让结构看起来完整"而把叙述性内容硬翻成表格。
